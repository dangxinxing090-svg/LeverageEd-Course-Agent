## 一、数据库层改进

### 1.1 自动 Fallback 机制

**原设计**: 仅支持 PostgreSQL，需手动配置和启动

**改进后**: 支持 PostgreSQL 与 SQLite 双模式，自动检测和切换

```
启动流程:
1. 读取 DATABASE_URL 环境变量
2. 检测 PostgreSQL 是否可连接
   ├─ 可连接 → 使用 PostgreSQL
   └─ 不可连接 → 自动 fallback 到 SQLite
3. SQLite 启用 WAL 模式，避免 disk I/O 错误
```

**配置方式**:
- 方式一（PostgreSQL）: `DATABASE_URL=postgresql://user:pass@host:port/db`
- 方式二（SQLite，默认）: 不配置或留空，自动使用 `backend/ai_education.db`

**适用场景**:
| 场景 | 推荐数据库 | 说明 |
|------|-----------|------|
| 快速体验/开发测试 | SQLite | 无需安装额外服务，开箱即用 |
| 生产环境 | PostgreSQL | 支持高并发、事务完整性、数据备份 |

### 1.2 数据持久化

**新增表结构**:
| 表名 | 用途 |
|------|------|
| `teaching_sessions` | 教学会话管理 |
| `chat_messages` | 聊天记录存储 |
| `exercise_records` | 练习答题记录 |
| `learning_paths` | 学习路径数据 |
| `users` | 用户信息 |

**初始化命令**:
```bash
cd backend
python init_database.py
```

## 二、知识体系生成流程优化

### 2.1 原流程（V1.0）

```
用户提交主题
    ↓
后端并行调用两个 LLM（asyncio.gather）:
    ├─ 全景介绍 Agent → 输出全景介绍文本
    └─ 知识拆分 Agent → 输出三层知识体系 JSON
    ↓
全部完成后一次性存入内存缓存（knowledge_cache）
    ↓
前端通过 SSE 轮询等待（最长 120 秒）
    ↓
超时或完成后显示内容
```

**问题**:
- 并行调用总耗时长（2-5 分钟），容易超过 120 秒超时限制
- 全部完成后才推送，用户长时间无反馈
- 内存缓存重启后数据丢失

### 2.2 优化后流程（V1.1）

```
用户提交主题
    ↓
Step 1: 生成全景介绍（30-60秒）
    ├─ 调用 LLM 生成全景介绍
    ├─ 完成后立即缓存（文件缓存 + 内存缓存）
    └─ SSE 推送 stage: "overview_done"
    ↓
Step 2: 生成知识结构（60-180秒）
    ├─ 调用 LLM 生成知识拆分
    ├─ 解析 JSON → 生成 UUID → 缓存
    └─ SSE 推送 stage: "completed"
    ↓
持久化到本地文件（topic_name 为 key）
```

### 2.3 SSE 流式推送增强

**原设计**: 仅支持 `completed` / `timeout` 两种状态

**改进后**: 支持三阶段状态推送

| stage | 含义 | 前端行为 |
|-------|------|----------|
| `processing` | 正在生成全景介绍 | 显示"AI正在分析主题..." |
| `overview_done` | 全景介绍已可用 | 先显示全景介绍，继续等待知识结构 |
| `completed` | 全部完成 | 显示完整知识体系和全景介绍 |
| `timeout` | 300秒超时 | 检查本地缓存，有数据则显示，否则提示刷新 |

**超时时间**: 从 120 秒延长至 300 秒

### 2.4 错误容错机制

**新增 fallback 策略**:

| 步骤 | 失败场景 | fallback 行为 |
|------|----------|---------------|
| 全景介绍生成 | LLM 调用失败 | 使用默认文本 `"## {主题名}\n\n正在准备学习内容..."` |
| 知识结构生成 | LLM 调用失败 / JSON 解析失败 | 使用默认知识结构（2个知识块、4个知识点） |
| 文件持久化 | 磁盘写入失败 | 仅使用内存缓存，不影响前端展示 |

## 四、知识讲解生成修复

### 4.1 问题背景

从全景知识图谱页点击知识点跳转到学习页后，讲解内容不显示；点击"下一个"按钮后，讲解被重复请求多次，页面出现重复的讲解内容。

### 4.2 问题一：Prompt 与代码期望不匹配

**根因**: `EXPLAIN_JSON_PROMPT` 要求 LLM "格式自由发挥，不要受固定模板约束"，但 `explain_knowledge_json` 方法和 `sessions.py` 端点期望返回 `{"sections": [{"icon": "...", "title": "...", "content": "..."}]}` 格式的 JSON。

**实际结果**: LLM 返回 `{"content": "..."}` 格式，代码解析后 `sections` 为空列表，API 返回 `{"error": "生成讲解内容为空"}`。

**修复方案**: 修改 `EXPLAIN_JSON_PROMPT`，明确要求 LLM 返回包含 `sections` 数组的 JSON 格式，每个 section 包含 `icon`（emoji）、`title`（标题）、`content`（详细内容）三个字段。

**涉及文件**: `backend/app/agents/learning/unified_teaching_agent.py`

### 4.3 问题二：讲解重复加载

**根因**: 点击"下一个"按钮后，`loadExplanation` 被调用多次（实测多达 5 次），原因包括：

1. **React StrictMode** 导致组件渲染两次，`useEffect` 执行、清理、再执行
2. **`initSession` 被多次调用**（`topicId` 和 `initialComponentId` 变化的时间不同步），每次都重置 `lastLoadedComponentRef.current = ''`
3. **`useEffect` 依赖过多**（`sessionLoading`、`shouldAutoLoad`、`currentComponent?.componentId` 等），多个状态变化导致多次触发
4. **`lastLoadedComponentRef` 失效**：每次重置后条件判断永远为 `true`，无法阻止重复调用

**修复方案**: 三层防重机制

| 层级 | 机制 | 说明 |
|------|------|------|
| 第一层 | `isLoadingExplanationRef` | ref 标记当前是否正在加载讲解，`loadExplanation` 入口处检查，防止并发调用 |
| 第二层 | `shouldAutoLoad` 自动关闭 | `loadExplanation` 成功后执行 `setShouldAutoLoad(false)`，防止 `useEffect` 因 `shouldAutoLoad` 变化再次触发 |
| 第三层 | `useEffect` 依赖优化 | 移除稳定的 `loadExplanation` 引用，添加 `isLoadingExplanationRef.current` 条件检查 |

**涉及文件**: `frontend/src/components/TeachingPanel/ChatTeachingPanel.tsx`

### 4.4 修复前后对比

| 指标 | 修复前 | 修复后 |
|------|--------|--------|
| explain API 调用次数（点击下一个） | 5 次 | 1 次 |
| 讲解内容显示 | 空白或重复 | 正常显示 |
| Prompt 返回格式 | `{"content": "..."}` | `{"sections": [...]}` |

## 五、后续优化建议

1. **预置热门主题缓存**: 对"Python编程"、"数据分析"等热门主题预置完整 mock 数据，实现秒开
2. **任务队列**: 引入 Celery + Redis 处理 LLM 调用，支持任务重试和状态追踪
3. **增量更新**: 知识结构支持增量更新，避免全量重新生成
4. **多模型负载均衡**: LLM 调用支持多 Provider 轮询，提升可用性
